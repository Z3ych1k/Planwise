## 二、第一阶段：补充边界与跨模块测试——最简单的例子

假设用户有一项 **22:00 到次日 06:00 的跨夜固定日程**（如夜班），同时有一个需要 **1 小时**的清晨任务。

* `events.py`：负责把跨夜日程在 `24:00`（1440 分钟）处拆成当晚和次日清晨两段。
* `timetable.py`：负责为任务寻找空闲时间格，必须避开被日程占用的时段。

| 测试场景 | 测试输入 | 预期系统行为 |
| :--- | :--- | :--- |
| 跨夜日程拆分与阻挡 | `D0` 设为无空闲；固定日程为 `D0 22:00` 至 `D1 06:00`（`1320–1800`）；任务需 `60` 分钟。 | 次日 `00:00–06:00` 被占用，任务只能从 **`06:00`（360 分钟）**开始排程。 |
| 香港法定假日与双休规则 | 2026-01-01（元旦）至 2026-01-04（周日）期间分别设置 `workdays` 与 `holidays` 重复事件。 | `workdays` 仅在 **1 月 2 日（周五）**触发；`holidays` 正确匹配元旦与周六、周日。 |
| 重复取消同一跨夜场次 | 对同一跨夜日程的 `D0` 场次连续调用两次 `cancel_occurrence()`。 | 第一次同时移除当晚与次日清晨两半段；第二次直接抛出 **`ValueError`** 拦截。 |

**一句话解释：** 不仅测“正常输入能不能跑通”，更专门测“跨午夜、遇假期、输错值”这些最容易出 Bug 的边界情况。

## 三、第二阶段：为什么修改测试条件，而不是改业务代码？

在运行新增测试时，曾出现个别断言失败（例如香港假日测试中 `2026-01-03` 周六被算入非工作日，以及跨夜测试中任务提前在当天排完）。

经过逐行核对 `events.py` 和 `timetable.py` 的实现后发现：

* **业务代码逻辑本身是完全正确的**：系统严格遵循“周一至周五为默认工作日”以及“优先从最早可用日期开始排程”的设计规则。
* **问题出在测试前置条件（Fixture）不够严谨**：测试时没有清空当天的默认空闲窗口，导致任务根本没有进入次日清晨的跨夜阻挡检测。

**最终决定：** 保持核心业务代码零妥协，直接通过设置 `s['availability'] = {D0: [], D1: [[0, 600]]}` 和 `s['capacity']` 隔离测试窗口，让测试精准验证目标场景。

**这也是 Testing & Code Review 的价值：** 区分“真正的程序缺陷”与“测试数据假设偏差”，避免为了迎合不严谨的测试而改坏原本正确的业务代码。

## 四、第三阶段：文档规范（Docstrings）与 CI/CD 流水线

为了满足课程评分标准中 **Excellent（Documentation & Code Review）** 以及 **Bonus（AI 辅助测试与 CI/CD）** 的要求，我完成了两项工程化收尾：

| 工程实践 | 修改前 | 修改后 |
| :--- | :--- | :--- |
| 代码文档（Docstrings） | 部分测试方法与辅助函数缺少注释，他人难以一眼看出测试目的。 | 统一补全标准 Google 风格文档字符串，写明测试目标（如 `Edge case:`、`Boundary test:`）、输入参数与返回值。 |
| 自动化测试流水线（CI/CD） | 每次修改后需手动跑命令，网页编辑或合并代码时容易漏掉导入或标点符号。 | 接入 GitHub Actions，每次 `git push` 自动运行全部 **138 项单元测试**，任何 SyntaxError、ImportError 或断言失败都会立即红灯报警。 |

**用生活例子记：**

* **单元测试（138 项）** = 全面体检表：把正常功能、边界条件和错误输入逐项检查一遍。
* **Docstrings 文档** = 说明书标签：让每个函数和测试用例不用读内部代码就知道它的用途和规则。
* **GitHub Actions CI/CD** = 自动门禁：每次提交代码自动跑完 138 项体检，全绿才算安全过关。
